Get started with Citius

Run the reference server and sign with a key that you create from a scope. Or link the C library into your process. Then find the reference documentation.

Three ways to use Citius

All three follow the same specification. The concepts are the same in each.

  • Run the server

    Run citius-server on localhost:50051, with in-memory keys and no authentication. Try it with grpcurl in five minutes.

  • Call it from Go

    The Go SDK gives Go clients for the services, with TLS, bearer tokens and YAML configuration.

  • Link it into C

    libagilecrypto runs the same API in your process. It has agc_* C headers and a Rust implementation.

Quickstart: sign, then move the key to ML-DSA

This quickstart takes about five minutes. You need grpcurl and jq. You run the reference server and create a policy and a key from a scope. Then you sign, verify and move the key to a quantum-safe template.

1. Run citius-server

git clone https://github.com/agile-crypto/citius-server
cd citius-server
make run-dev    # gRPC on 127.0.0.1:50051 with reflection, no authentication, no TLS

2. Save the policy as policy.json

{
  "version": "1",
  "allowed_templates": [
    "ecdsa-p256-sha256-der",
    "ml-dsa-65"
  ],
  "allowed_operations": {
    "key_operations": [
      "create_key", "read_key", "sign", "verify"
    ]
  }
}

3. Create, sign, verify, transform

# 2. create a policy: it lists the templates that its keys can use
jq -Rs '{name: "prod-signing", policyDocument: .}' policy.json   | grpcurl -plaintext -d @ localhost:50051 caas.crypto.v1.CryptoPolicyService/CreateCryptoPolicy

# 3. create a key from a scope: a standard signature, no algorithm
grpcurl -plaintext -d '{"name": "contract-signing-key", "policy": "prod-signing",
  "scopeSpec": {"signature": {"scope": "SIGNATURE_SCOPE_STANDARD"}}}'   localhost:50051 caas.crypto.v1.KeyManagementService/CreateKey | jq '.keyMetadata | {templateId, version}'

# 4. sign with the key name ("contract v1" in base64), then verify
grpcurl -plaintext -d '{"keyName": "contract-signing-key", "input": "Y29udHJhY3QgdjE=", "noContext": {}}'   localhost:50051 caas.crypto.v1.CryptoService/Sign > sig.json
jq '{keyName: "contract-signing-key", input: "Y29udHJhY3QgdjE=", signature, metadata, noContext: {}}' sig.json   | grpcurl -plaintext -d @ localhost:50051 caas.crypto.v1.CryptoService/Verify | jq '{valid}'

# 5. move the key to a quantum-safe template. The Sign request does not change.
grpcurl -plaintext -d '{"name": "contract-signing-key",
  "scopeSpec": {"signature": {"scope": "SIGNATURE_SCOPE_STANDARD", "security": {"quantumSafe": true}}}}'   localhost:50051 caas.crypto.v1.KeyManagementService/TransformKey | jq '.keyMetadata | {templateId, version}'

The commands return these results:

# step 3
{ "templateId": "ecdsa-p256-sha256-der", "version": 1 }
# step 4
{ "valid": true }
# step 5
{ "templateId": "ml-dsa-65", "version": 2 }

Run the Verify command of step 4 again after step 5. The old signature is still valid against key version 1. A new Sign uses key version 2 and makes an ML-DSA-65 signature of 3,309 bytes.

The server keeps keys in memory. When you restart the server, the key store is empty.

In-process from C

libagilecrypto is the C API, written in Rust. You need a Rust toolchain, libclang for bindgen and a C compiler. The install command writes the library, the headers, a pkg-config file and a CMake package.

git clone https://github.com/agile-crypto/citius-c-api
git clone https://github.com/agile-crypto/citius-rust
cd citius-rust
cargo xtask install --prefix /opt/agilecrypto
cc app.c $(pkg-config --cflags --libs agilecrypto)
find_package(agilecrypto 1.0 REQUIRED)
target_link_libraries(app PRIVATE agilecrypto::agilecrypto)

The examples/c/ folder in citius-rust has three small programs: encrypt and decrypt, sign and verify, and a persistent key store. By default, keys stay in memory. To keep them on disk, set key_store_uri to a file: directory and supply a 32-byte wrapping key.
