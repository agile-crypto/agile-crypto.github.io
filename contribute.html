Contributing to Citius

You can open issues and pull requests on every repository. This page shows the setup for each repository, the procedure for a specification change and how to report a vulnerability.

Ways to contribute

  • Report a bug or a missing feature. Open an issue on the related repository. Include the component, the version and the platform.
  • Add a provider or a template. Write a new backend for citius-server, or a catalog entry with its security properties.
  • Write a client in another language. Use the protobuf specification. The Go SDK is an example.
  • Improve the documentation. There are no guides yet for policies, the key lifecycle or post-quantum migration. You can write them.
  • Do research. You can review and extend the assessment framework and the design principles.

Development setup

citius-server (Go)

make build      # compile all packages
make test       # unit tests
make test-race  # with the race detector
make lint       # golangci-lint and buf lint
make ci         # lint, race tests and smoke tests, required before a merge

citius-rust (Rust and C)

cargo test --workspace   # unit, architecture and header-pin tests
cargo xtask test-c       # rebuild the library, run the C tests without and with ASan+UBSan
cargo xtask all          # test-c, Miri, TSan and the Go interoperability tests
git config core.hooksPath .githooks   # pre-push: clippy, tests, test-c

Miri and TSan need a nightly toolchain in addition to the default toolchain: rustup toolchain install nightly --component miri --component rust-src. The interoperability tests need Go and a citius-server clone in the same parent folder.

citius-c-api (headers)

cmake -S . -B build
cmake --build build      # fails if any header does not compile on its own
ctest --test-dir build --output-on-failure

api (protobuf)

cd proto && ./build_proto.sh   # Go, gRPC gateway and OpenAPI output

Changes to the specification

Four implementations follow the protobuf specification, so each change to it starts as a proposal. Write the proposal as an RFC in the style of PROTO_RFCS.md. Then open an issue on the api repository. Proposed C functions stay in agc_ext.h, behind AGC_ENABLE_PROPOSED_EXTENSIONS, until the specification includes them.

An automatic check compares the C headers with a pinned copy of the specification. Each RPC must map to exactly one C function. DIVERGENCES.yaml records each intentional difference and its reason.

Report a vulnerability

Do not report security problems in public issues. Use the private vulnerability reporting of GitHub on the affected repository: open Security, then Report a vulnerability. Include the component, the version or commit, and the steps to reproduce the problem.

Citius is a research prototype. Do not use it in production. There is no commitment to a response time yet.

Community and support

Send questions, ideas and bug reports as issues on the related repository at github.com/agile-crypto. All code is under the Apache License 2.0.

The repositories do not have a contributing guide, a code of conduct or contributor terms yet. This page will link to them when they are available.
